Fase 6A — Nuestro laboratorio vs Scramjet real

Esta fase no añade transporte ni acceso remoto. Su objetivo es ubicar las piezas que construimos en las fases anteriores dentro de la arquitectura publicada de Scramjet y distinguir una analogía educativa de una implementación completa.

← Volver a Fase 5D Laboratorio principal
Scramjet real tiene muchas más superficies que este laboratorio: instrumentación del entorno del navegador, rewriter dedicado, manejo de fetch/headers/body, sandboxing, controladores y transports. Aquí solo comparamos responsabilidades; no cargamos su runtime ni abrimos sockets a destinos lógicos.

Matriz de equivalencias

Responsabilidad Nuestro laboratorio Scramjet publicado Equivalencia
Reescribir URLs phase5a.html: atributos HTML/CSS y una simulación de fetch() packages/core/rewriter Parcial
Runtime del cliente Solo una función educativa labFetch(); no parcheamos APIs globales packages/core/src/client, incluyendo DOM, location y worker helpers Muy parcial
Intercepción sw.js + rutas __lab_route__, __lab_transport__, __lab_wisp__ Core de Scramjet combina intercepción con su propia capa fetch/runtime Conceptualmente cercana
Fetch / request handling GET fijo, respuesta sintética y MessageChannel packages/core/src/fetch separa body, fetch, headers, parse y util Simplificada
Transport Adapter local → WebSocket Echo Core depende de @mercuryworkshop/proxy-transports Interfaz análoga
Wisp framing CONNECT/DATA/CLOSE auténticos, pero solo eco Base64 El ecosistema de MercuryWorkshop usa transports y Wisp en herramientas relacionadas; un servidor real interpreta frames y realiza I/O Wire format, no backend
Socket al destino No existe Necesario en una implementación proxy completa Deliberadamente ausente

Qué sí y qué no hemos construido

Sí

✓ Service Worker interceptando requests reales del mismo origen ✓ URL rewriting controlado ✓ separación entre URL visible y URL lógica ✓ MessageChannel como frontera SW ↔ adapter ✓ WebSocket persistente ✓ multiplexación y estados de stream ✓ frames Wisp v2 de laboratorio ✓ handshake y flow control simulados

No

✗ runtime completo de instrumentación web ✗ cobertura de todas las APIs del navegador ✗ manejo real de cookies/CORS/headers de sitios remotos ✗ servidor Wisp operativo ✗ TCP/UDP hacia destinos lógicos ✗ navegación arbitraria ✗ proxy funcional
